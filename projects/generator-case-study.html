In 30 seconds

The problem

A learning game has limited value if every new subject requires a developer, a Unity project and a new build.

What we built

A web authoring system where content editors define a game, create matching pairs using text and images, validate the content and publish it to the database used by the game.

The result

One game engine can serve an unlimited number of games. Published content becomes immediately available through an entry code, without modifying Unity.

The generator screens

Five views cover the complete editor workflow.

01 / 05
DASHBOARD · EMPTY STATE

A clear first action

Specification. First-time editors see an empty state rather than an empty table, with one direct action for creating their first game.

Design rationale. The focused message and illustrated character reduce uncertainty and make the next step unmistakable.

02 / 05
MY GAMES DASHBOARD

Manage everything in one place

Specification. Each row exposes the game name, entry code, pair count, publishing state and actions. Tooltips explain publishing conditions, and publishing is physically blocked below ten pairs.

Design rationale. A table supports comparison without endless scrolling. Columns follow the editor’s decision order, while color-coded pair counts communicate readiness.

03 / 05
GAME SETTINGS

Validated configuration

Specification. Name, instructions and response time define the game. Character counts update in real time, excess characters are blocked, and Save remains unavailable until every rule is met.

Design rationale. The same traffic-light convention used in the dashboard creates continuity. Response time uses a closed menu because only fixed values are valid.

04 / 05
PAIR EDITOR

Create and manage matching pairs

Specification. Pair creation sits beside the existing-pair library. Each item can be text or image. Selecting one type locks the other. Editing imports a pair into the workspace, while deletion and leaving with unsaved changes require confirmation.

Design rationale. Disabled actions remain visible in gray, showing what is available while making an incomplete state clear.

05 / 05
SETTINGS POPUP

Edit without breaking the flow

Specification. Game settings can be updated without leaving the pair editor. Real-time validation ensures that only valid changes can be saved.

Design rationale. The modal preserves context. A dedicated “Save changes” action replaced the ambiguous global Save button, giving every save action one responsibility.

Shared visual languageThe generator intentionally adopts the game’s palette, buttons and illustration style, so the editor and the player experience feel like two parts of one product.

03

Authoring-system benchmark

Three quiz and matching-game generators were reviewed. Six recurring patterns became specification decisions.

3Authoring systems6Design decisions
Minimum content

10 pairs before publishing

The dashboard shows how many pairs remain and physically disables publishing below the threshold.

Controlled time values

30, 40 or 50 seconds

A closed list prevents invalid values and simplifies configuration.

Text or image

One content type per item

Each item can contain either text or an image. Once one type is selected, the other input is locked, keeping the choice clear and preventing conflicting content.

Irreversible actions

Confirmation before deletion or publishing

Critical actions require explicit confirmation.

Unsaved work

Protect work before leaving

If an editor tries to leave with unsaved changes, a confirmation dialog explains that the work will be lost and asks them to confirm the exit. The workspace resets only after a successful save.

Field validation

Prevent invalid input, not only flag it

Color alone cannot prevent incorrect input. Character limits block excess typing, and Save remains locked until every field meets its requirements.

04

Architecture and data model

The system separates content management from gameplay and connects both environments through one data layer.

AUTHORING PATH
Blazor WebAssembly→ASP.NET Core API→Dapper repository→SQLite database

The browser client sends editor actions to the API. Controllers validate ownership and business rules before Dapper reads or updates the relational data.

PLAY PATH
Unity WebGL→Game code endpoint→Published-game validation→Game + pairs + items

Unity requests a game by its entry code. The server verifies that it exists and is published, then returns its settings, pairs and items as one playable structure.

05

Selected product iterations

Seven changes aligned the editing workflow with the learning rules, reduced ambiguity and prevented avoidable errors.

ITERATION 01

Completion threshold

BeforeEditors could set a 10–100% completion threshold.

AfterThe slider was removed. Finishing now always requires all pairs.

ITERATION 02

Instruction length

BeforeInstructions were limited to 5–50 characters.

AfterThe range expanded to 15–90 so editors could write complete guidance.

ITERATION 03

Edit without leaving the workspace

BeforeChanging the name, instructions or response time forced editors to leave the pair editor. This interrupted the workflow and could put unfinished work at risk.

AfterA settings popup keeps editors in context. Its dedicated Save action also makes it clear which changes are being saved.

ITERATION 04

Visible image-size limit

BeforeThe upload field stated only the accepted file type, PNG or JPEG, without a maximum size.

AfterA clear 4MB limit appears before upload, preventing oversized files that could harm loading performance and the interface experience.

ITERATION 05

Specific deletion warning

BeforeThe warning asked only whether to delete a game.

AfterIt identifies the selected game and its question count before deletion.

ITERATION 06

Direct editor access

BeforeEditors reached the authoring environment through the player entry path.

AfterA permanent “For Editors” link provides direct access from the main navigation.

ITERATION 07

A clearer action hierarchy

Before“My Games,” “Save Game,” and “Settings” appeared as three equally prominent controls above the pair editor. They competed with the primary actions for saving and editing a pair. In addition, “Save Game” was redundant — its purpose was to save the game with the new changes, but this action was already handled by the “Save Pair” button.

AfterThe redundant “Save Game” control was removed. “My Games” and “Settings” remained, but were given less visual prominence so they no longer compete with the primary actions of creating and editing a pair. They became secondary actions on the page, keeping the focus on the pair currently being created or edited.

One endpoint connects Unity to the authored content. One business rule prevents incomplete games from being published.
